The batch sweep

TX_BATCH_MAX_PACKETS sets how many 9-byte metric records may accumulate in a W5500 transmit buffer before SEND is issued. A datagram costs a fixed nine-transaction SPI sequence whatever it carries, so N records in one datagram divides that cost by N. That is the whole mechanism, and it shows up as a clean 1/N curve in the per-metric cost.

Sustained = the highest offered rate whose loss stayed at or under 0.1 %, reported as what was actually delivered. Where the load lands stopped mattering

All three placements — spread across eight sockets, one socket on 9217 (FIFO 0, top arbiter priority), one socket on 9219 (FIFO 3) — land within a rung of each other. The ceiling therefore sits upstream of the priority arbiter, which has nothing to arbitrate while only one channel is active. Past the knee the difference appears: the eight-socket spread degrades gradually, a single hot socket falls off a cliff.

Is it repeatable, and what happens above the knee?

The ladders are single-shot, which locates a knee but says nothing about spread — and two runs disagreed about the shape above it. Repeating each rate five times settles it.

CAN, and both at once

The FPGA is the device under test; the Nucleo is only a traffic source. Its own counter for frames that never reached the bus separates “the FPGA lost it” from “it was never sent”, and across the whole ladder the FPGA line stays at zero: the CAN path is bus-limited, not FPGA-limited. Its real ceiling is still unmeasured, and finding it needs a faster bus — CLKS_PER_BIT in top.vhd with matching STM32 bit timing, a change to two subsystems that was left alone here.

Run together, the two inputs share one transmit chip and one arbiter. Adding 1,400 frames/s of CAN costs Ethernet a few thousand packets/s spread over eight sockets and roughly three times that on a single socket.

Whether Ethernet can starve CAN depends on the batch size, and that is the part worth carrying away:

The transmit-buffer livelock

CHECK_IF_FREE_SIZE_IS_AVAILABLE has no way out. Below minimum_free_tx_buffer_memory (256 bytes) it returns to GET_TX_FREE_BUFFER_SIZE and re-reads the same socket. Nothing advances the socket counter, nothing falls through to the receive branch, and there is no retry budget. The watchdog cannot see it, because it zeroes on every state change and this alternation changes state on every SPI transaction.

Both halves are now confirmed rather than argued. The stall runs 42.6 ms at its worst against a 2.18 ms watchdog threshold, and the SPI bus is never idle for more than 25 clocks throughout — so cs_idle_max, the liveness measure every other testbench relies on, registers nothing at all. Across the run no Sn_RX_RSR read occurs, by construction: any other transaction would have ended the run.

How far away is it?

The livelock starts once the chip's wire cost reaches 200 µs per datagram (340 back-to-back Sn_TX_FSR reads, 1.16 ms). As built it is about 5 µs, and 100 µs still recovers cleanly. So the link has to be roughly 40× slower than 100 Mbit before this is reachable — which is why the bench has never produced it, and why this is a simulation result and not a measurement.

Why no existing testbench could have found it

tb_w5500_tx's behavioural chip frees the entire transmit buffer the instant SEND is written, so Sn_TX_FSR is never low and the branch is unreachable at any wire speed. Modelling the buffer as freeing only once the wire has carried the bytes — which is what the chip does, since free space is not free until it has been sent — is the entire difference. The sweep runs both models, so that comparison is in the output rather than in a claim.

All at a wire cost of 1 ms per datagram unless the row says otherwise — about 200× slower than the 100 Mbit link as built. “Min free” is the lowest Sn_TX_FSR the controller saw; the threshold it compares against is 256 bytes.

The asymmetric case is the one the concern was actually about, and it is the only one that reproduces it. Feeding two sockets evenly never stalls at all — spreading the load halves the pressure on each socket's own buffer. Drive one socket hard and give a second socket a trickle, and the second socket gets two to four datagrams out while the first gets twenty-five: its traffic is stuck behind a full buffer it has nothing to do with. That is panel (d).

Three consequences worth acting on. A 256-byte transmit buffer never transmits at all: free space can never exceed the 256-byte threshold, so the comparison is never satisfied. Larger batches are safer, not riskier — fewer trips through the check, more bytes retired per wire transaction. And a single hot socket is the dangerous shape: spreading load gives each socket its own buffer and the stall never starts.

What the old harness was measuring

Four defects, all on the measurement side, found while setting this up. They matter because the numbers in the previous README were produced with them.

  • 90,112 probes, then the step stops. The sequence number hides in one device's safe band, so at 150 kpps the window was 0.6 s. The probe key is now (port, identifier, seq) across eight identifiers on eight ports: 5.8 M probes, with every value still inside 1–89 °C so no test packet can trip the interlock.
  • Sender and receivers shared a GIL. A bare sendto loop reaches 381 k pps on this host, but the old ceiling test asked for 1.4 M pps and achieved 90 k at zero loss — the ceiling in that CSV was the harness.
  • SO_RCVBUF was a no-op. It asked for 8 MiB; net.core.rmem_max here is 212,992, so the kernel granted ~0.4 MiB.
  • Any unknown identifier counted as CAN. At overload the mis-framed datagrams decode to arbitrary identifiers, which inflated CAN arrivals past CAN sends and produced negative loss — the giveaway that the attribution was wrong rather than the board generous.

One limit that is not a defect but bounds every Ethernet number here: enp2s0 is 1 Gbit while both W5500s are 100 Mbit, so above 148,810 packets/s the switch discards. A 9-byte UDP payload is a 64-byte frame plus preamble and inter-frame gap — 84 bytes, 672 bits. Steps above that are run and plotted, never used for a sustained-rate claim.

Framing integrity above the knee

Past the knee the return path emits datagrams whose length is not a multiple of 9 bytes, and datagrams carrying more records than the configured batch allows. Since the configured ceiling is the number of records the controller will put in a datagram, anything above it is mis-framing. The host discards a datagram whose length is not a multiple of 9, so these register as loss — but a consumer that parsed them optimistically would ingest garbage metric values instead, and in an interlock system a mangled value can assert a global interlock from nothing. The rate is strongly batch-dependent, which points at the transmit pointer and length bookkeeping under backpressure rather than at the batching logic.
